# VNPyKit 0.1.0 alpha 1 release plan

Target identities:

- Python: `vnpykit==0.1.0a1`
- npm: `@vnpykit/protocol`, `@vnpykit/renderer`,
  `@vnpykit/runtime-pyodide`, `@vnpykit/embed`, and `@vnpykit/cli`, each
  at `0.1.0-alpha.1`
- executable: `vnpykit`
- Git tag and GitHub release: `v0.1.0a1`
- repository: `visionnumbers/vnpykit`

No step below is authorized by this document. Tagging, pushing, staging,
publishing, changing visibility, or creating a GitHub release requires separate
owner authorization.

## Preparation order

1. Review, commit, and push the M4.1 changes under separate authorization.
2. Confirm the pushed commit with a successful CI run and rerun the build-only
   workflow. Download its artifacts and compare every hash with the reviewed
   candidate.
3. Complete trademark/domain review and the outstanding manual accessibility
   checks.
4. Select a repository protection strategy. The current private-repository plan
   cannot provide branch protection or required environment reviewers.
5. Configure the PyPI pending Trusted Publisher as documented in
   `v0.1.0-alpha.1-registry-bootstrap.md`.
6. Obtain explicit authorization, create and push signed tag `v0.1.0a1`, then
   run `release.yml` with `publish=false`. Review the resulting artifacts.
7. Obtain a second explicit authorization immediately before any upload. A
   publishing dispatch must set `publish=true` and enter the exact workflow
   phrase `PUBLISH VNPYKIT 0.1.0 ALPHA 1`.

## Registry order

1. Publish Python through the PyPI pending Trusted Publisher and verify project,
   version, file hashes, repository link, and attestations.
2. Perform the npm first-publication bootstrap in dependency order:
   protocol, renderer, runtime-pyodide, embed, CLI. Every command must use
   `--access public --tag alpha`.
3. Verify each npm version, public access, exact repository URL, integrity, and
   `alpha` dist-tag before continuing.
4. After all packages exist, configure a Trusted Publisher separately on every
   npm package. Configure it only when a follow-up version can validate the new
   connection within npm's two-day expiry window.
5. Prefer stage-only Trusted Publisher permissions when the workflow is migrated
   to `npm stage publish`; otherwise explicitly allow direct `npm publish`.
   Do not grant dist-tag management unless the workflow needs it.
6. Restrict traditional npm publishing to 2FA and disallow tokens after OIDC is
   validated.
7. Create the GitHub prerelease only after both registries have been verified.

The alpha npm tarballs intentionally omit explicit provenance while the source
repository is private. npm Trusted Publishing generates provenance
automatically only for a public package published from a public repository.

## Failure response

- PyPI: stop the workflow, yank the affected release, keep the immutable version
  and Git history, and publish a corrected higher version.
- npm: stop before the next dependent package; deprecate the faulty version and
  move the `alpha` dist-tag to a corrected higher version. Use unpublish only
  when npm policy permits and an emergency justifies it; never reuse a version.
- GitHub: do not move or rewrite the signed tag. Withdraw incorrect release
  presentation if necessary, retain evidence, and publish a corrected prerelease
  from a new version/tag.
- Any hash, ownership, OIDC, or permission mismatch is a hard stop.
